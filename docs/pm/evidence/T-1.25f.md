# T-1.25f evidence: reader rollback on mid-file corruption and tampered shots (DEF-005, plan 1.25)

Logs: `T-1.25f-1.log` (snapshot + interface tests), `T-1.25f-2.log` (AC-2 demo),
`T-1.25f-3.log` (startup cost), `T-1.25f-4.log` (ruff, format, mypy), `T-1.25f-5.log` (full suite).

## Chosen approach: full checksum check on first open, digest cache per process

`LiveSnapshotStore` now defaults to `full_check=True` and calls
`open_current(cfg, full_check=True, cached=True)`. `health_check(..., cached=True)` hashes files
through `ingest.snapshots.sha256_cached`, a per-process dict keyed by
`(resolved path, st_dev, st_ino, st_size, st_mtime_ns, st_ctime_ns)`. `publish` and direct
`open_current` callers keep the uncached path (unchanged default `cached=False`).

Why checksums rather than a scan-based check:

- A scan cannot verify shots content at all: the manifest checksum is the only thing that pins
  the Parquet bytes, and the done-when names tampered shots.
- A DuckDB scan only detects corruption in blocks it actually reads. `count(col)` can be answered
  from validity masks or statistics, and the old `count(*)` probe was answered from metadata,
  which is how DEF-005 slipped through. A complete scan would have to touch every column of every
  table, which costs the same order as hashing (measured below) and still says nothing about
  shots.
- Checksums are what the build already records, so there is one definition of "healthy" for
  publish and for the reader.

Why the cache is safe: an in-place rewrite changes `st_mtime_ns` and `st_ctime_ns` (ctime cannot be
set from user space), and a replacement changes the inode. Hard-linked unchanged shot seasons share
an inode with the previous snapshot, so a nightly swap hashes only the new database and the
changed seasons. `test_reader_digest_cache_misses_on_in_place_rewrite` covers a same-size,
same-inode corruption after a clean first open; `test_reader_reuses_digests_of_unchanged_files`
shows a second open hashes nothing.

The reader runs the check only when `current` points at a new snapshot ID (first request, swap,
rollback), not per request; that behaviour is unchanged.

## Startup cost (T-1.25f-3.log)

Machine: MacBookPro18,3 (Apple M1 Pro). Largest available build: `data/build/dev.duckdb` +
`data/build/dev_shots` (3 files, 200,648,781 bytes). No published snapshot exists under
`data/snapshots/`.

| Check | Time |
| --- | --- |
| Old probe (`count(*) from marts.games`) | 0.8 ms |
| SHA-256 of all files, uncached (3 runs, warm page cache) | 0.123 s / 0.099 s / 0.098 s |
| `sha256_cached` first call | 0.100 s |
| `sha256_cached` hit (later open) | 0.11 ms |
| Scan alternative (count every column of all 39 tables) | 0.106 s |

About 2 GB/s, so roughly 0.5 s per GB on first open. A full-history snapshot several times the dev
build's size would still be a few seconds once per process start or swap. Cold-cache reads were not
measured (purging the page cache needs root); SSD read speed on this machine is the same order.

## Known limit

A writer that restores size, mtime and ctime cannot be caught by the cache; ctime restoration needs
changing the system clock (root). A process restart always re-hashes.
